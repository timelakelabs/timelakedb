What it does, measured

Every number below comes from the same 36.6-million-event day run through the benchmark harness in this repository — the same dataset every other engine was given.

Blazing fast

211 ms → 0 ms

Median product lookup across 36.6M events, cold. Once footers are cached the same lookups return in 0–6 ms, because immutable Parquet metadata prunes files without fetching them.

Efficient storage

0.50 GB / day

Columnar Parquet with entity-clustered compaction: less than half the InfluxDB 3 footprint for the same data, and roughly a sixteenth of what the 1.x and 2.x TSM engines wrote.

Never killed by a query

0.68 s

The cross-product aggregation that OOM-killed InfluxDB 1.8 returns here in under a second. One shared memory pool, admission control and server-side deadlines make that a structural property, not luck.

Specified from evidence

This database exists because five engines ran one identical workload — ~1–2M products a day moving through ten pipeline steps, queried with COUNT(DISTINCT product_id) — and their failures defined the requirements.

Quick start

Docker is the only prerequisite. The server speaks InfluxDB line protocol on 1963, Flight SQL on 1964, and serves its management console on 1963 at /admin/ui.

Run it 
# from a clone of the repository
cd TimelordDB/bench
docker compose -f compose/timelorddb.yml up -d --build
curl http://localhost:1963/health
Write a point 
curl -i -X POST 'http://localhost:1963/api/v2/write?bucket=poc' \
  --data-binary 'pipeline_events,product_id=p-1042,step=01-download,worker_ip=172.16.1.7 event="start" 1754600000000000000'
# HTTP/1.1 204 No Content  — durable in the WAL before it returns
Query it 
curl -s -X POST http://localhost:1963/api/sql \
  -H 'content-type: application/json' \
  -d '{"db":"poc","sql":"SELECT step, COUNT(DISTINCT product_id) AS products FROM pipeline_events GROUP BY step ORDER BY step"}'

Point a stock Telegraf influxdb_v2 output at the same URL, or add Grafana's InfluxDB datasource in SQL mode against port 1964 — both work unmodified. To manage retention on the running server, open http://localhost:1963/admin/ui and sign in — the first run seeds admin/admin and makes you replace it before anything else works. The documentation covers ingestion, querying, retention, the console and operations in detail.
