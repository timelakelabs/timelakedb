TimeLakeDB

Time. Stored. Forever.

A time-series database for high-cardinality data

For when the number of distinct things you are tracking outgrew the memory you have — and you need to say exactly how long each table keeps its data. Built in Rust on Apache DataFusion, Arrow and Parquet.

Pre-v1 Single-node today, cluster-ready by design · Telegraf-compatible ingest · Grafana over Flight SQL · TLS 1.3 with hot certificate rotation · Encryption at rest · Authenticated admin console · Row visibility labels

Three things it promises

Each one is a structural property of the design rather than a tuning guide — something you should not have to configure your way into.

Cardinality costs a column

no series index

Tags are Arrow dictionary columns from the write path to the file. Nothing in memory grows with the number of distinct tag combinations, so a million distinct ids a day is a compressed column rather than an index you have to budget for.

Data on your terms

per-table retention

Retention is set per table and changed at runtime, not a global knob chosen at install time. Columnar Parquet with entity-clustered compaction keeps what you kept small, and drops what you did not.

Never killed by a query

bounded by design

Every query runs inside one shared memory pool, behind admission control, under a server-side deadline. A query too large to fit fails and says so; the process it was running in stays up.

How it is put together

Object-store native, columnar throughout, with one narrow seam for every byte that leaves the process.

WALdurable before the write is acknowledged
Arrowcolumnar buffers, dictionary-encoded tags
Parquetimmutable files, compacted in the background
Manifest logthe object store is the source of truth

A write is parsed, made durable in a write-ahead log, and applied to an in-memory columnar buffer before the server answers. Buffers become immutable Parquet; a manifest log records what exists. Queries run through Apache DataFusion over both at once, so rows are visible as soon as they are acknowledged rather than after the next flush.

Because the object store holds the data and the catalogue, a node carries nothing that cannot be rebuilt. Delete one, point a new one at the same bucket, and it serves.

Pre-v1, and honest about it. There is no released version yet, no compatibility promise between commits, and features arrive one at a time behind their own tests. Read the documentation for what is built today and the security posture before deploying anything.

Quick start

Docker is the only prerequisite. The server accepts line protocol on 1963, answers Flight SQL on 1964, and serves its management console on 1963 at /admin/ui.

Run it 
# from a clone of the repository
cd TimeLakeDB/bench
docker compose -f compose/timelakedb.yml up -d --build
curl http://localhost:1963/health
Write a point 
curl -i -X POST 'http://localhost:1963/api/v2/write?bucket=poc' \
  --data-binary 'pipeline_events,product_id=p-1042,step=01-download,worker_ip=172.16.1.7 event="start" 1754600000000000000'
# HTTP/1.1 204 No Content  — durable in the WAL before it returns
Query it 
curl -s -X POST http://localhost:1963/api/sql \
  -H 'content-type: application/json' \
  -d '{"db":"poc","sql":"SELECT step, COUNT(DISTINCT product_id) AS products FROM pipeline_events GROUP BY step ORDER BY step"}'

Point a stock Telegraf influxdb_v2 output at the same URL, or add Grafana's InfluxDB datasource in SQL mode against port 1964 — both work unmodified. To manage retention on the running server, open http://localhost:1963/admin/ui and sign in — the first run seeds admin/admin and makes you replace it before anything else works. The documentation covers ingestion, querying, retention, the console and operations in detail.
