Overview

TimeLakeDB is a time-series database for high-cardinality event analytics: millions of distinct entities per day, queried across their whole journey rather than one series at a time. It is written in Rust on Apache DataFusion, Arrow, Parquet and object_store.

Status: pre-v1. A single node is production-shaped — durable writes, compaction, retention, backup and restore, TLS with hot certificate rotation — and the same binary runs as a role-split cluster: ingester pairs that replicate before the ack, a stateless write router, and stateless queriers, each drilled. The compactor role is built but not yet startable, automatic failover is not built, and the intra-cluster link is plaintext on a private network. Read Scaling before planning a deployment.

The data plane can authenticate, but ships off. Set TIMELAKE_DATA_AUTH to optional or required and writes, /api/sql and Flight SQL all authenticate by token. Until you do, the default is off: any client that can reach port 1963 or 1964 reads and writes everything, and network reachability is your only access control. The admin surface always requires a session. Read Security before exposing this anywhere.

Why it exists

Two problems, both of which show up late and hurt: the number of distinct things you are tracking grows until the memory needed to index them is memory you do not have, and the data you are obliged to keep gets tangled with the data you are obliged to delete.

So tags are dictionary-encoded columns rather than entries in a series index, every query runs inside a bounded memory pool that fails the query instead of the process, and retention is a per-table setting you change at runtime. Each of those is checked by an acceptance test rather than asserted here.

How a write becomes a queryable row

  • Line protocol is parsed and appended to a write-ahead log, which is fsynced before the 204 returns — an acknowledged write survives a kill.
  • Rows land in a per-table in-memory buffer where tags are Arrow Dictionary<Int32, Utf8> columns. High-cardinality tags cost what a compressed column costs; nothing is keyed per series.
  • Flushes sort by primary key, apply last-write-wins de-duplication and write Snappy Parquet partitioned by (table, UTC hour).
  • A manifest-log catalog records file additions and removals; it is replayed at boot, so recovery is a log replay, not an index rebuild.
  • Compaction merges small files per partition, clustering rows by the highest-cardinality dictionary column so later queries can skip most row groups on statistics alone.

How a query stays inside its budget

Reads union the live buffer with catalogued Parquet through DataFusion. Files are pruned by time bounds, then by row-group statistics, then by decode-time row filters; immutable footers are cached so a warm lookup prunes without fetching anything. Every query runs against one shared memory pool, behind an admission semaphore and a server-side deadline — the hard invariant is that no query may kill the server.

Quick Start

Install a package, or run the container — neither needs a Rust toolchain.

Install (Debian / Ubuntu, RHEL / Rocky / Amazon Linux 2023) 
# .deb and .rpm are attached to every release
sudo apt install ./timelakedb_0.1.0~alpha_amd64.deb
# or: sudo dnf install ./timelakedb-0.1.0~alpha-1.x86_64.rpm

# The package binds 127.0.0.1 and does NOT start on install: the data
# plane is unauthenticated by default, so starting it is your decision.
sudo systemctl enable --now timelakedb
curl http://127.0.0.1:1963/health
Or start the container 
git clone https://github.com/timelakelabs/timelakedb.git
cd timelakedb
docker compose -f deploy/compose/timelakedb.yml up -d --build
curl http://localhost:1963/health
# {"status":"pass","name":"timelakedb",...}
Write and read back 
curl -X POST 'http://localhost:1963/api/v2/write?bucket=poc' \
  --data-binary 'pipeline_events,product_id=p-1042,step=01-download,worker_ip=172.16.1.7 event="start" 1754600000000000000'

curl -s -X POST http://localhost:1963/api/sql \
  -H 'content-type: application/json' \
  -d '{"db":"poc","sql":"SELECT COUNT(*) AS n FROM pipeline_events"}'

Telegraf

A stock agent needs a URL and nothing else — the token, organization and gzip defaults are all accepted.

[[outputs.influxdb_v2]]
  urls = ["http://timelakedb:1963"]

Grafana

Add the stock InfluxDB datasource, choose SQL as the query language, and point it at http://timelakedb:1964 — Grafana's Flight SQL client connects unmodified. The provisioned dashboards under fixtures/grafana/ are the compatibility fixture and render as-is.

Ingestion

All three InfluxDB write endpoints are accepted so existing agents and scripts need no changes. The database (or bucket) named in the query string is created on first write.

EndpointSelectorNotes
POST /write?db=v1-style
POST /api/v2/write?bucket=v2-style; org accepted and ignored (single tenant)
POST /api/v3/write_lp?db=v3-style

Request handling

  • Content-Encoding: gzip is decompressed automatically — the Telegraf influxdb_v2 default.
  • precision may be s, ms, us or ns (default). Points without a timestamp take server time.
  • 204 No Content means the batch is durable in the WAL, not merely buffered.
  • 400 identifies the offending line and field rather than failing the batch silently.
  • 429 with Retry-After is backpressure: the WAL has reached TIMELAKE_WAL_MAX_BYTES and flushing needs to catch up. It is a named, visible limit — writes are never dropped quietly.

Schema rules

Tags become dictionary-encoded string columns and fields become typed columns; new columns may appear at any time. One key is reserved: time is the timestamp column, so a tag or field named time is refused with a 400 rather than colliding with it. Rows sharing a primary key (tag set plus timestamp) are de-duplicated last-write-wins at flush, and again across files during compaction.

The exact grammar, escape set, field-type syntax, timestamp precisions and error messages are in the line protocol reference.

Querying

Two interfaces, one engine and one memory budget behind them.

SQL over HTTP

POST /api/sql 
curl -s -X POST http://localhost:1963/api/sql \
  -H 'content-type: application/json' \
  -d '{"db":"poc","sql":"SELECT step, COUNT(DISTINCT product_id) AS products
                     FROM pipeline_events
                     WHERE time >= now() - INTERVAL '\''24 hours'\''
                     GROUP BY step ORDER BY step"}'

The response is a JSON array of row objects. SQL is DataFusion's dialect — the SQL reference lists what is supported, what is not (no INSERT/DELETE; data leaves by retention or by an administrator's targeted delete), and how each type is encoded on the wire. SHOW TABLES, DESCRIBE and information_schema all work for schema discovery.

Flight SQL

Port 1964 serves Arrow Flight SQL for Grafana and any Flight SQL client. The database is read from request metadata — database, bucket-name, bucket or db, in that order — and defaults to poc.

What makes it fast

  • Time pruning: partition bounds eliminate whole files before any I/O.
  • Statistics pruning: entity-clustered compaction means a single product's rows sit in a handful of row groups, and min/max statistics skip the rest.
  • Bloom filters on high-cardinality tag columns answer "this entity is definitely not in this file" without reading any of it — which is what prunes freshly written data, where statistics ranges still span every entity. Low-cardinality tags get none: a value present in every file cannot be excluded, so the filter would be pure cost.
  • Row filters and projection pushdown: predicates are applied during decode, and only referenced columns are materialised.
  • Metadata cache: Parquet footers are immutable, so a repeat lookup prunes from cache and reads only surviving files — 0–6 ms warm against roughly 300 ms cold.

Guardrails

Queries share one FairSpillPool, queue behind an admission semaphore, and are cancelled at a server-side deadline; loads run on the blocking pool so a slow scan can always be preempted. Size the pool below the container memory limit divided by the admission count.

Retention

Retention is configured per table, not globally — metrics that matter for a year and debug streams that matter for three days live in the same database without compromise. It is set two ways: the system property below seeds it at startup, and the admin console changes it on a running server without a restart.

Per-table retention 
TIMELAKE_RETENTION="poc.pipeline_events=365d,poc.host_metrics=90d,disk_metrics=72h"
  • Policies are scoped by database and table: db.table=…. A bare table name is the all-databases wildcard (*.table) and the most specific policy wins. Retention used to match on table name alone, which expired every same-named table on the node — a data-loss bug fixed 2026-08-19; stored policies from before then were migrated to the wildcard so their behaviour did not change on upgrade.
  • Durations take d (days), h (hours), or a bare number of seconds.
  • Tables absent from the specification are kept indefinitely; an empty value keeps everything. The node's own _system telemetry tables get no default policy either — bounding them is one PUT, and deliberately yours to make.
  • Enforcement drops whole (table, hour) partitions on the maintenance tick — it is a catalog operation, not a row-by-row delete.
  • Removed files are deleted only after TIMELAKE_GC_GRACE_SECS (default 900 s) so a long-running query's catalog snapshot can never dangle. Keep the grace longer than TIMELAKE_QUERY_TIMEOUT_SECS.

Background maintenance runs on one sequential task: flush checks every 10 s, compaction every 30 s, retention every 60 s, so housekeeping can never stack up on itself.

Admin Console

A management page ships with the server at http://<host>:1963/admin/ui — self-contained HTML from the binary itself, no build step, no external assets, and no separate deployment. It signs you in, makes you replace the first-run password, and then manages what the server does at runtime.

The console shares port 1963 with the data plane today. Every /admin/* route requires a session, but the port is the same one your writers use — so keep 1963 private and treat console reachability as an access-control decision. A dedicated, privately bound admin listener is designed and phased as U0; see Ports and exposure.

First run: sign in, then rotate

With no principals configured the server seeds admin / admin and quarantines it: the only route that answers is POST /admin/password, and everything else returns 403 password_change_required until the password changes. Rotating it ends every session for that principal — including the one that just rotated it — so you sign in again with the new password.

  • The new password must be at least 8 characters, and cannot be the username or the word admin.
  • Set TIMELAKE_ADMIN_BOOTSTRAP_PASSWORD to provision a real password at first start instead of the well-known default.
  • Alert on timelake_admin_default_credential_active — a 1 means the seeded credential is still live.

Roles

RoleCan do
viewerRead the console and every /admin/* GET. Changes nothing.
operatorEverything a viewer can, plus non-destructive changes — including growing a retention window.
adminEverything an operator can, plus the destructive direction — shrinking, introducing or removing a retention window — and POST /admin/tls/reload.

The split follows the data rather than the verb: growing a window keeps more, shrinking one destroys history. That is why introducing a policy on a table that had none is an admin action — it is a deletion in disguise.

What it manages today

Retention (FR-7), scoped per database and table: the active policies with all-databases wildcards called out, a set/remove form with table-name completion, the live timelake_retention_drops_total counter, and an explicit warning that shrinking a window deletes data on the next enforcement pass — permanently once TIMELAKE_GC_GRACE_SECS elapses. Changes persist through the object store (catalog/config/retention.json, encrypted with everything else) and survive a restart, so the stored policy outlives a stale TIMELAKE_RETENTION in your compose file. Data-plane tokens (SEC-4): issue, list and revoke, with the secret shown exactly once.

Everything else the admin plane does is API-first for now — targeted delete, the audit trail, certificate grants and TLS reload are curl against /admin/* with a session, listed under API Reference. Metrics and performance views exist as a Grafana console rather than a page in this one: the node stores its own telemetry in _system and deploy/compose/timelakedb-console.yml provisions the dashboard that reads it (port 3004). Layered configuration with visible provenance and a cluster view are designed but not built — the phases are U0–U3 in ARCHITECTURE.md §14, specified in docs/CONSOLE.md.

Planned (U0): the admin plane gets its own listener on 1965, bound to 127.0.0.1 by default, and /admin/* leaves 1963. The most destructive endpoints should not inherit the data plane's exposure. Until then, the port you publish for writes is the port that reaches the console.

Security

The honest version: transport encryption (TLS 1.3 with hot rotation), want-mode client certificates, encryption at rest including the WAL, row visibility labels, a hash-chained audit trail, and authentication on both the admin surface and the data plane are finished and drilled — but the data plane ships with authentication off. Until you set TIMELAKE_DATA_AUTH, access control for writes and queries is network isolation, and visibility authorizations are claims any client can assert. Plan the deployment around the default you actually run, not the one the mechanism allows.

Authentication covers administration always, and data only when you turn it on. Every /admin/* route requires a session with a role (viewer, operator, admin). The data plane — writes, /api/sql, Flight SQL — authenticates by token when TIMELAKE_DATA_AUTH is optional or required; under the default off the Authorization header is not examined, so any token works and so does none, and the Flight SQL handshake accepts anything. There are no per-table permissions; databases are namespaces, not security boundaries. On a default install treat an open 1963 or 1964 as equivalent to an unauthenticated shell into the data. The default is off because flipping it is a breaking change for every client not yet holding a token — Telegraf and Grafana included — and optional exists so the flip can be staged on a measured split (timelake_data_requests_*) rather than taken blind.

Those guardrails bound resource exhaustion; they are not access control. No query can kill the server, but any client can run one.

Exposures that follow

The authoritative list, with the reasoning behind each, is SECURITY.md. What remains open:

  • The data plane is unauthenticated by default. With TIMELAKE_DATA_AUTH unset, anyone who can reach 1963 or 1964 can write arbitrary data, read all data and enumerate the schema. Setting required closes it, but that breaks every client not yet holding a token — which is why off is still the default and optional exists as the migration state between them. Until you set it, treat the port as an unauthenticated shell into the data.
  • The administrative surface answers on the same port as the data plane (1963), and a deployment that never rotates the seeded admin/admin credential is one guess from an admin role that can delete history. The seeded credential may do nothing but change its own password, and timelake_admin_default_credential_active reads 1 until it does — but the mitigation is procedural, not structural.
  • Visibility authorizations are self-asserted on the anonymous path: X-TimeLake-Authorizations: admin is a claim any client can make. A data-plane token's grants and a verified client certificate both narrow it, and both are optional under the default settings, so an attacker simply declines to present one.
  • Want-mode client authentication grants nothing on its own, by design — an attacker takes the anonymous path. Its value is that an authenticated caller can be held to less.
  • The intra-cluster listener is unauthenticated and serves rows, so reaching it is equivalent to read access to the object store itself. Keep it on a private network.
  • Encryption at rest protects the media, not the query surface: anyone who can reach /api/sql reads decrypted data. That is authentication's job, not encryption's.

Closed since earlier drafts of this page, and no longer exposures: the COPY … TO write primitive (the SQL surface is read-only, enforced on the logical plan), the root container (it runs as an unprivileged user with a read-only root filesystem), verbatim query errors (now one opaque reference), the missing per-client rate limit, and the plaintext WAL.

Deploying it safely

  • Bind to localhost or a private network — TIMELAKE_ADDR=127.0.0.1:1963 — and publish nothing to an untrusted network. That address carries the console as well as the write API, so it is the only lever over who can reach either.
  • If remote access is needed, front it with something that authenticates. Flight SQL is gRPC over HTTP/2, so a proxy in front of port 1964 must speak HTTP/2; a proxy in front of the console must forward cookies and the X-TimeLake-CSRF header.
  • Provision the first administrator with TIMELAKE_ADMIN_BOOTSTRAP_PASSWORD rather than letting the seeded admin/admin exist at all, and alert on timelake_admin_default_credential_active.
  • Enable TLS even on a private network — rotation costs no downtime — and set TIMELAKE_ENCRYPTION_KEY so a lost volume or leaked bucket is ciphertext. Keep the key out of the data volume, and treat losing it as losing the data.
  • Give it a dedicated volume and a container memory limit.

SECURITY.md in the repository carries the full posture, the vulnerability reporting process and the roadmap; REQUIREMENTS.md §8 is the specification behind it.

Backup & Restore

The whole database is one directory — TIMELAKE_DATA_DIR, holding the write-ahead log, the Parquet objects and the manifest-log catalog. Copying it is the backup. ops/tldb-backup.sh does that through a throwaway helper container, so Docker is the only prerequisite.

Back up, verify, restore 
./ops/tldb-backup.sh backup                     # live, no downtime
./ops/tldb-backup.sh verify  -f timelake-backup-20260808-214500.tgz
./ops/tldb-backup.sh restore -f timelake-backup-20260808-214500.tgz --recreate

Why a live backup is safe

  • Objects are written before the manifest that references them, so a snapshot may contain an object no manifest mentions — invisible, harmless — but never the reverse.
  • Every object is written temp, fsync, rename: a manifest entry is durable or absent, never torn.
  • A truncated WAL tail is tolerated per generation, so capturing a segment mid-append costs at most the frame being written — which was never acknowledged to a client.
  • A file removed from the catalog is deleted only after TIMELAKE_GC_GRACE_SECS, so the archive is internally consistent as long as the backup finishes inside the grace period, which the 900 s default leaves considerable room for.

Quiescing writes (--stop <container>) removes even that window. It is not required.

Measured

StepResult
AT-5 full scale: backup / restore34 s / 13 s, 36.68M rows exact — against 10–15 min on the 1.x incumbent

Scaling

One node

The default, TIMELAKE_ROLE=all: one process handles ingest, query, compaction and retention together, and sustains writes while queries run concurrently. The vertical levers are the query memory pool, the admission count, the flush size and the compaction trigger — each of which is a named setting rather than a heuristic, so what the node will do under pressure is something you configure rather than discover.

A cluster: one binary, four roles

The same binary runs as a role-split cluster over one shared object store (TIMELAKE_OBJECT_STORE=s3://…), each role arriving with its own recorded drill. Topology is static for now: TIMELAKE_PEERS lists every node as id=role@cluster_addr|data_addr, and TIMELAKE_CLUSTER_ADDR is the private intra-cluster listener an ingester opens for its peers. The reference rig is deploy/compose/timelakedb-cluster-s3.yml: a router, two ingesters, two queriers and LocalStack on one bucket.

TIMELAKE_ROLEDoesState
routerStateless. Holds no data, opens no engine. Shards each line-protocol body by (db, measurement) across the ingesters and forwards; forwards /api/sql round-robin to the queriers, falling through on a transport failure. A peer that is down degrades loudly (timelake_cl2_degraded) rather than failing writes. Refuses writes (501). A commit fence already makes two compactors correct (a merge whose inputs were replaced is refused); what is missing is the work-avoidance that makes them efficient, so the role refuses to start until then. Compaction runs on an all-role node meanwhile

A cluster stays the same database from outside — the same write endpoints, the same SQL, the same Grafana datasource. Two caveats the drills made explicit: the router checks every line has a measurement, gzip and UTF-8 for the whole body before it forwards anything, but a line that fails field-level parsing is refused by the one ingester that receives its shard, so a body spanning several shards can land partially; and a router forwards writes without the client's Authorization header, so ingesters behind a router cannot run TIMELAKE_DATA_AUTH=required today. Queries do carry the header through.

What the cluster is built on, and what is still open

  • The catalog is an append-only manifest log whose commits are compare-and-swap on the next sequence (put_if_absent, S3 If-None-Match), so two writers on one bucket lose nothing — drilled on both the local and S3 mechanisms (catalog-cas-drill.log). Discovery never carries correctness; that stays here.
  • All object I/O passes through one narrow store interface — which is how encryption at rest arrived as a decorator rather than a rewrite, and how S3 with KMS envelope keys did (TIMELAKE_OBJECT_STORE, TIMELAKE_KMS_KEY_ID). Parquet modular encryption would land at the same seam.
  • Node discovery is a trait: a static backend now, Consul later (C3).
  • Recovery after an ingester dies is explicit — an operator or the router calls POST /internal/v1/recover on the peer. Automatic health-triggered failover is not built.
  • The intra-cluster listener is plaintext HTTP with no authentication and no visibility filter; required mTLS on it is a C3 decision. Keep it on a private network (see Security).
  • Changing the ingester count moves most table homes. Drain the agents first — docs/REBALANCE.md says which gauges to wait on and which obvious one not to.

Sizing guidance

Set a container memory limit and keep TIMELAKE_QUERY_MEM_BYTES × TIMELAKE_MAX_CONCURRENT_QUERIES inside it — that product is the ceiling queries can reach, so it is the number the limit has to accommodate. A useful starting point is a pool of roughly 40% of the container limit with 2 admitted queries, then widen once you know your query shapes.

Metrics

Types, meanings and suggested alerts are in the metrics reference, which lists every series. In outline: the engine (timelake_lines_written_total, timelake_flushes_total, timelake_compactions_total, timelake_retention_drops_total, timelake_parquet_files, timelake_buffer_rows, timelake_wal_bytes, timelake_databases, timelake_tables); the query side — timelake_query_duration_seconds and timelake_query_admission_wait_seconds histograms, in-flight and queued gauges, and finished / timed-out / refused / failed counters; lifecycle — uptime, timelake_build_info, flush and compaction lag, timelake_files{level}, per-table timelake_storage_{bytes,rows}, timelake_write_rejected_total{reason}. TLS adds timelake_tls_cert_expiry_seconds and timelake_tls_last_reload_ok; the admin surface adds timelake_admin_default_credential_active, timelake_admin_logins_total and timelake_admin_login_failures_total; data-plane auth adds timelake_data_auth_mode and the timelake_data_requests_* split. Targeted delete adds timelake_tombstone_rewrites_total; the audit trail adds timelake_audit_records_total and timelake_audit_sink_healthy; the per-client cap adds timelake_query_rate_limited_total; row visibility adds timelake_visibility_rows_filtered_total; each cluster role adds its own (timelake_cl2_*, timelake_querier_*, timelake_router_*). The same numbers are stored in _system.metrics for SQL and Grafana; /metrics stays the alerting surface because it answers from in-memory counters when the query path is what is broken.

Alert on timelake_audit_sink_healthy == 0. It means the audit sink cannot append, and because the trail is fail-closed that is also the reason administrative changes are being refused with 503.

TLS and certificate rotation

Setting TIMELAKE_TLS_CERT and TIMELAKE_TLS_KEY puts TLS 1.3 on both listeners. Certificates are designed to be short-lived: overwrite the files (a certbot deploy hook, a sidecar, anything) and a watcher picks the change up within seconds, or call POST /admin/tls/reload. A replacement is parsed and validated — PEM structure, expiry, and that the key matches the certificate — before an atomic swap, and the resolver is consulted only during a handshake, so rotation never disturbs established connections or in-flight queries. A bad renewal keeps the last-good pair serving and logs the named alarm SEC3_CERT_RENEWAL_FAILED while timelake_tls_last_reload_ok drops to 0.

Best Practices

Give the container a memory limit

Always set mem_limit (or the Kubernetes equivalent) and keep the pool times admission inside it. This is not defensive paperwork: during development an unbounded runaway scan took down an entire Docker VM and every container on it.

Use real volumes, not host bind mounts

On Windows and macOS, a bind-mounted data directory cost roughly three seconds per query in file-read overhead alone. Use a named volume or native storage.

Alert on certificate health, not on the calendar

Page on timelake_tls_last_reload_ok == 0 and on timelake_tls_cert_expiry_seconds falling below roughly two renewal periods. The server will keep serving on the last-good certificate, which is exactly why a silent failure would otherwise go unnoticed until expiry.

Back up while running, and restore before you need to

Objects are written before the manifest that references them, so a live snapshot is internally consistent — a backup taken under load restored with every row exact in 13 seconds. Run ops/tldb-backup.sh from cron, and rehearse the restore into a scratch volume at least once: a backup nobody has restored is a hypothesis. See Backup & Restore.

Assume the port is the perimeter until you turn auth on

Administration is always authenticated; the data plane is only when TIMELAKE_DATA_AUTH says so, and it ships off. Until you set it, whoever can reach 1963 or 1964 owns the data — and because the console answers on 1963 too, that port also decides who can reach the management surface. Bind to a private interface, keep TimeLakeDB off any network you do not control, rotate the seeded credential, stage optional → required while watching timelake_data_requests_anonymous_total, and read Security in full before a deployment. In a cluster, the intra-cluster listener is the port that must never be published.

Prove changes with the harness

Gauge — the benchmark harness, its own repository under timelakelabs — is the executable specification. Run python bench/bench.py run --backend timelakedb --scale laptop from a Gauge checkout and compare against its recorded baselines with bench/bench.py compare rather than inventing a new measurement each time; that is how every performance figure on this site was produced. Correctness verdicts come from Catchment, the conformance harness, and the drill transcripts under docs/evidence/ in this repository — deliberately a different source, so the wrong one never gets quoted for the other.
