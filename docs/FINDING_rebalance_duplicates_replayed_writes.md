# A rebalance during an outage turns replayed writes into served duplicates

**Found 2026-08-13** by Catchment's `router-tributary-exactness` (C4),
third run — the run its recorded prediction was written for: *"partial
acknowledgement is where this breaks, if it breaks."* It broke there.

---

## The symptom

Eight Tributary streams of 200,000 lines through the router. Mid-flight,
ingester-b is frozen (SIGSTOP — sockets open); while it is frozen the
cluster is rebalanced from two ingesters to three (router and queriers
recreated with the widened peer list); then b thaws and the agents'
spooled batches re-ship through the new topology.

| Table | stream's home during freeze | rows | distinct |
|---|---|---|---|
| seam_t04, t06 | ingester-a (never frozen) | 200,000 | 200,000 |
| seam_t05, t07 | ingester-b (frozen) | **202,000** | 200,000 |

2,000 excess rows per affected table — exactly 4 batches × 500 lines —
and nothing missing. The kill-and-replay phase of the same run, at
constant N, was exact on all four of its tables. The run is its own
control twice over: the a-side streams also spooled a few batches (the
router recreate dropped their connections) and their same-home replay
deduplicated perfectly.

Evidence:
`catchment/results/router-tributary-exactness-20260813-231355/run.json`.

---

## The cause

Four correct mechanisms compose into a wrong count:

1. A request in flight to a frozen node can LAND WITHOUT AN ACK: the
   kernel buffered the bytes, the client timed out, the thawed node
   digests and stores — and tells a dead socket.
2. The agent retries the whole spooled batch. Its idempotency is real
   but implicit: it relies on the retry landing on the SAME node, where
   flush-time LWW dedup collapses the overlap. Nothing writes that
   assumption down, and nothing enforces it.
3. `shard_of` is FNV-1a **mod N**. Changing N moves roughly (N-1)/N of
   all table homes, so the retry lands on a different node than the
   original.
4. Cross-node duplicate primary keys meet only at compaction — and a
   partition compacts at `compact_min_files` (default 4), which two or
   three files never reach. The querier's union serves both copies,
   confidently, until then. Potentially forever.

Same failure direction as the catch_up race and the double-recover
finding, found by the same suite in the same day: a COUNT inflated with
full confidence — the exact inverse of the failure this database was
specified to prevent.

Tributary is blameless here, and so is each component in isolation. The
stamper regenerated byte-identical timestamps on replay — the primary
keys were perfect. The seam is that primary-key idempotency is only as
good as the guarantee that twins eventually MEET, and a stateless remap
severs it.

---

## Paths to closing it (a design decision, not a patch)

- **Overlap-aware compaction** (recommended): compact a partition's
  files when their time ranges overlap, regardless of file count.
  Overlapping ranges in one partition are exactly the twins case; it
  also closes the recover-crash-window tail
  (`FINDING_recover_not_idempotent.md`) and bounds the duplicate window
  at one compaction pass instead of "maybe never".
- **Consistent hashing in the router**: a ring moves ~1/N of homes on a
  membership change instead of (N-1)/N. Reduces incidence, does not
  eliminate the window.
- **A drain discipline for rebalances**: operationally, the duplicate
  requires spooled batches in flight across the membership change. A
  runbook rule — quiesce agents / drain spools before changing N — makes
  the current behaviour safe, in the same way recover is an explicit
  operator step. Cheapest, weakest: it guards the planned rebalance,
  not the unplanned one.

## Status

**Open.** The C4 scenario asserts exactness across an undrained
rebalance and will stay red until the composition holds; that standing
red is the deliverable — it is the difference between a known limitation
and a forgotten one. The kill-and-replay half of the seam (constant N)
is proven exact and is not implicated.
